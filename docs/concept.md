# Концепция Aestetic UI

## Обещание продукта

Собирать административные интерфейсы из понятных готовых решений: аккуратно, последовательно и без повторного изобретения навигации, структуры и базового оформления в каждом проекте.

Первая реализация предназначена для Laravel/Blade. Дизайн-правила и описания компонентов отделены от конкретного приложения, чтобы в будущем допускать другие адаптеры без обещания их поддержки сейчас.

## Для кого

- Пользователь админки: находит нужный раздел, понимает состояние и доступные действия, сохраняет контекст при переходах.
- Разработчик: выбирает готовую композицию, настраивает её слотами и параметрами, легко находит реализацию и стили.
- Codex: получает точные контракты, правила выбора и примеры для версии установленного пакета, не придумывая собственные props и локальные варианты оформления.

## Визуальный характер

Спокойный, ясный, собранный интерфейс. Сдержанная типографика, нейтральные поверхности, выразительная иерархия и небольшой набор акцентов. Красота поддерживает чтение и выполнение задач.

Цвет бренда, шрифт и часть характера могут настраиваться темой. Структура, значения ролей, качество состояний и согласованность действий сохраняются. Точные палитры, размеры и визуальное направление выбираются на этапе эталонных экранов; оформление референса не считается окончательной темой.

## Навигация как часть первого выпуска

- Общая оболочка и понятное положение пользователя в системе.
- Основные разделы и группы; вложенность только при реальной структуре продукта.
- Различимые глобальная навигация, вкладки объекта, breadcrumbs и локальные действия.
- Переносимые active/expanded состояния; доступность с клавиатуры и на телефоне.
- Переходы список → объект → редактирование → возврат с сохранением контекста, которым управляет приложение.
- Основное действие страницы, вторичные операции и необратимые действия имеют согласованные роли.

Библиотека получает разрешённые пункты и URL от приложения. Она не решает самостоятельно, какой пользователь имеет доступ к данным.

## Иерархия как структура, а не набор случайных чисел

| Отношение | Владелец |
| --- | --- |
| Подпись, контрол, подсказка, ошибка | Field |
| Поля одной смысловой группы | FieldGroup / Fieldset |
| Группы и пояснения формы | FormSection |
| Заголовок раздела и содержимое | Section |
| Заголовок страницы и рабочая область | Page |
| Основная область и боковая панель | PageLayout |
| Интервалы и читаемость набора данных | Table / DescriptionList |

Сначала выбирается смысловая композиция; она задаёт расстояния и типографические роли. У заголовка различаются визуальная роль и уровень HTML-heading. Нельзя получить хорошую иерархию одним большим словарём spacing-токенов.

## Три эталонных экрана

1. Список заказов: поиск, фильтры, сортировка, строки, состояния, пагинация и массовые действия.
2. Карточка клиента: характеристики, вкладки связанных данных, действия, длинные значения и отсутствие данных.
3. Форма редактирования: секции, группы, подсказки, ошибки, сохранение и отмена, возможная боковая панель.

Предметные названия — синтетические примеры, не встроенные сущности продукта. Одна оболочка и правила работают во всех трёх сценариях. Нужны обычное, пустое, ошибочное, недоступное и загрузочное состояния, длинные тексты, узкая ширина и клавиатура.

## Что делает каталог

Показывает реальные компоненты и примеры страниц, состояния, тему, плотность и адаптивность. Для компонента объясняет назначение, альтернативы, API и копируемый код. Для композиции объясняет логику управления и иерархию.

## Что делает интеграция с Codex

Даёт агенту возможность найти сценарий, изучить подходящие компоненты и собрать интерфейс по правилам библиотеки. Машинное описание и человеческий каталог опираются на общие сведения одной версии.

MCP передаёт знания; решение о выборе принимает Codex. Надёжность повышают хороший каталог, точные контракты, готовые композиции и приёмка. Одно подключение MCP не гарантирует идеального результата во всех проектах.

## Границы

Продукт не хранит бизнес-данные, не генерирует обязательную структуру моделей, не подменяет ACL и не выполняет произвольные операции приложения. Поддержка всех потенциальных сценариев означает расширяемые границы и согласованные паттерны, а не огромный универсальный компонент с десятками флагов.
