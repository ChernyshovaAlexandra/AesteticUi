## 1. Эталонный интерфейс и иерархия

- Выбрать визуальное направление, шкалу типографики, семантические интервалы, темы и плотность.
- Сначала спроектировать структуру действий и навигации; затем форму представления.
- Продумать основную навигацию, вложенность, контекст объекта, breadcrumbs и мобильное раскрытие.
- Составить синтетические страницы заказов, клиента и формы, включая длинные данные и состояния.
- Записать правила выбора Section/Panel, Tabs/Navigation, Menu/Disclosure и основных/вторичных действий.

Результат: согласованное направление трёх экранов и правила, из которых выводятся компоненты. Ручная визуальная приёмка — отдельное свидетельство пользователя. До неё направление остаётся рабочим.

Подготовленный результат: [прототип](../design/reference/index.html), [инструкция](../design/reference/README.md), [правила и карта переходов](reference-design.md). Написаны общая навигация, список заказов, карточка клиента и форма с локальными взаимодействиями. Это артефакт дизайна, не Blade-workbench и не реализованный API компонентов. Визуальная приёмка ожидается; статус полного завершения этапа не установлен.

Дополнения U-15 и U-18: в исходниках прототипа подготовлены общие поля, собственный раскрывающийся Select, календарь и выбор времени; панель «Поля и выбор» показывает типы и состояния. Это реализация дизайн-прототипа; проверки, визуальная приёмка и перенос в Blade не выполнены.

Медиадополнение U-24 подготовлено на уровне дизайн-прототипа: сетка, слайдер с миниатюрами, карусель карточек, просмотр и блоки с изображениями. Примеры доступны через «Параметры макета → Галереи и изображения»; [контракты и границы](media.md). Проверки и визуальная приёмка не выполнены. Семейства добавлены в реестр как `planned`; перенос в Blade и определение версии поставки остаются отдельной работой.

Дополнение U-26: MediaCard выделен в общий renderer и CSS дизайн-прототипа; показаны отдельное размещение, сетка и карусель, а также необязательные части карточки. Запись `media-card` в реестре остаётся `planned`; требуется перенос в Blade. Проверки и визуальная приёмка не выполнялись.

## 2. Каркас: от компонента до Codex

Дополнение U-27: общие UI-renderers, Dialog/Tabs runtime и медиасемейства отделены от конкретных экранов и demo-данных. Написаны независимые примеры. Выполнена [статическая проверка исходников](reusability-review-2026-10-23.md); браузерная приёмка и перенос этих компонентов в Blade остаются отдельными работами.

- Создать Composer-каркас, provider, подключение готовых ассетов и минимальный Laravel-workbench в этом репозитории.
- Реализовать Scope/Page, Button и Input/Field в объёме небольшого примера.
- Добавить реальное Blade-rendering в каталог и описание реализованных контрактов.
- Создать минимальный read-only MCP: информация о версии, поиск, один компонент и одно правило.
- Подготовить инструкцию подключения без изменения глобальных настроек пользователя.
- Зафиксировать версии инструментов и зависимостей, формат каталога и связь метаданных с кодом.

Результат: короткая полная цепочка код → каталог → MCP. Наличие исходников не подтверждает установку или соединение. Запуски/приёмка — только в отдельно разрешённом объёме.

Частичный результат от 23 октября 2026: по поручению создать Composer-каркас без публикации подготовлены `composer.json` (`aestetic/ui`, PHP `^8.3`, Illuminate `^12.0`), provider с package discovery, конфиг темы/плотности, CSS с manifest/хешем и компоненты `assets`, `scope`, `page`, текстовый `button` (primary/outline, type, disabled). Контракты записаны в реестр как `experimental`; подготовлены [инструкция локального подключения](installation.md) и [Blade-пример](../examples/getting-started.blade.php). Установка, сборочная команда, проверки, публикация и подключение потребителей не выполнялись. Input/Field, полный Button, workbench, живой каталог и MCP ещё не реализованы; этап 2 не завершён.

Дополнение от 23 октября 2026 по поручению создать Laravel-workbench без публикации: в `workbench/` подготовлено Laravel-приложение, установлен framework 12.70.1 и корневой пакет через path/symlink, завершены package discovery и копирование CSS. Каталог читает общий реестр и 11 Blade-сценариев из `catalog/examples/`, показывает реальные компоненты в iframe, темы light/dark/system, плотность comfortable/compact, ширину preview, исходный Blade, API и planned-границу. [Подготовка и запуск](../workbench/README.md). Сервер/браузер и проверки не запускались, HTTP-rendering и визуальная приёмка не подтверждены. Публикация, внешние проекты и MCP не затронуты. Input/Field, полный Button и MCP остаются невыполненной частью этапа 2; этап целиком не завершён.

Дополнение U-CATALOG-01: создан обзор «Компоненты» и раздел подключения, атомарные элементы сгруппированы по задачам. Написаны Icon, Link, Spinner, Status, Input, Textarea, Select, Checkbox, Radio, Switch, FileInput, Avatar, Thumbnail; Button получил loading и пример icon-only. Реестр содержит guidance, API и 26 исполняемых Blade-сценариев. Готовые CSS/JS скопированы в локальный workbench. Исправлена показанная пользователем ошибка отсутствующего componentGroups. Проверки и браузерная приёмка новых изменений не выполнялись; статус experimental сохраняется. Field/Form, специализированные дата/время и MCP остаются невыполненными частями плана. ## 3. Основные элементы

- Реализовать действия, статусы, ошибки, собственные эстетичные контролы с нативной семантикой, Field/Fieldset, FormSection и действия формы. Для полей и Select соблюдать U-15 и [направление оформления](form-controls.md).
- Согласовать value/old/errors, nested names, массивы, `0`, disabled/readonly и multi-select.
- Добавить доступные имена, ARIA-связи, focus и нативную семантику.
- У каждого компонента одновременно появляются сценарии и API в каталоге/MCP.

Результат: форма собирается из общего слоя, без скрытых моделей и сетевых операций. API и ограничения документированы.

## 4. Оболочка и навигация

- Реализовать AppShell, Navigation/Group/Item, Page/PageHeader/PageLayout.
- Добавить breadcrumbs, Tabs, navigation disclosure, action menu и dialog с разными семантическими контрактами.
- Согласовать состояния active/expanded/selected, клавиатуру, несколько экземпляров, re-init/cleanup и responsive.
- Встроить смысловую иерархию отступов и заголовков в композиции.

Результат: три эталонных экрана используют одну понятную структуру. Отложить всю навигацию до следующих версий нельзя: это часть первого результата.

## 5. Данные и страницы

- Реализовать таблицу, сортировку, pagination/page-size, фильтры, selection и bulk actions.
- Обработать пустоту, ошибку, загрузку, длинные значения и узкий экран.
- Собрать готовые ListPage, DetailPage, EditPage из общих компонентов.
- Сохранять фильтры/возврат через явные URL и настройки приложения; не добавлять серверный CRUD внутрь библиотеки.

Результат: список, карточка и форма работают как связанные сценарии на синтетических данных. Полный универсальный resource builder не нужен.

## 6. Codex как потребитель системы

- Довести инструменты MCP до спецификации из `codex-mcp.md`.
- Добавить инструкции/навык выбора компонентов, правил и версий; навык ещё не считается установленным от наличия файла.
- Подготовить примеры заданий: список пользователей, карточка с длинными данными, форма с ошибками.
- Явно обрабатывать неизвестную версию, planned API и отсутствие подходящей композиции.
- По разрешённому заданию продемонстрировать фактическую цепочку MCP → выбор → Blade, не подменяя её ручной загрузкой всей документации.

Результат: агент может получить точный доступный API и подобрать паттерн. Стабильность и качество оцениваются на примерах, а не обещаются автоматически.

## 7. Первый выпуск 0.1

- Подготовить выпуск через GitHub + Packagist по U-24: выбрать GitHub owner/URL, окончательное Composer-имя и лицензию; подготовить публичный репозиторий, теги версий, регистрацию пакета в Packagist и синхронизацию выпусков. Внешние действия выполняются по отдельному поручению на публикацию.
- Зафиксировать фактический состав реализованного API, совместимость и политику обновления.
- Подготовить dist, инструкции установки/обновления/отката, лицензии и versioned snapshot каталога.
- Описать простой путь для любого Laravel-проекта пользователя в пределах заявленной совместимости: `composer require <окончательное-имя-пакета>`, автоматическая регистрация provider, публикация и подключение готовых CSS/JS, первый пример Blade-компонента. Установка не должна требовать ручного добавления VCS-репозитория или настройки сборки библиотеки в проекте-потребителе; точные команды определяются реализованным каркасом.
- Выполнить только запрошенные пользователем функциональные проверки изменённых контрактов. Не заменять визуальную приёмку CSS-assertions.
- Предоставить пользователю живой каталог/примеры для ручной оценки; агент не открывает браузер без разрешения.
- Выбрать отдельного реального потребителя, когда пользователь его назовёт; никакой проект не подключается автоматически.
- Публикация пакета, каталога, удалённого репозитория и MCP — отдельные явно разрешённые действия.

Результат: различимы готовность к выпуску, сам выпуск и реальное подключение. Невыполненные условия остаются в статусе, без объявления полной готовности.

## 8. Расширения

По конкретному сценарию: combobox, tree-select, image-picker/media-grid, gallery/image-slider/carousel/image-viewer, image-figure/image-block, repeater, rich-text, key-value-tree, command palette, дополнительные page-patterns. Для медиасемейств соблюдать U-24 и media.md; исходный прототип не заменяет Blade-реализацию. Они используют тот же реестр, правила, каталог и MCP.

В [анализе админки МТС-33](mts-33-admin-reference.md) предложена последовательность расширений: вложенный Repeater с доступной перестановкой, RichText и медиа → композиции редактора и модерации → аналитические блоки. Следующее предлагаемое дизайн-задание — синтетические редактор составного контента и карточка модерации. Это предложения для этапа 8 и дальнейшего проектирования; разработка этих экранов не начата, состав 0.1 не расширен. Связанные журналы, раздельные признаки состояния и даты с часовым поясом учитываются как варианты базовых таблиц/карточек этапа 5.

## Критерии приёмки по областям

| Область | Будущие свидетельства |
| --- | --- |
| Архитектура | Понятные владельцы, отсутствие бизнес-зависимостей, ясная цепочка от компонента до потребителя |
| Навигация | Узнаваемое положение, сохранение контекста, клавиатура, узкая ширина |
| Формы/таблицы | Функциональные контракты, значения и состояния, серверная обработка у приложения |
| Каталог | Реальные компоненты, примеры, темы, состояния, копируемый код |
| MCP | Версия, достоверный API, planned/unknown ответы, доступность без обязательного web-workbench |
| Эстетика | Ручная оценка иерархии, ритма, читаемости и удобства пользователем |
| Выпуск | Реальная установка и согласованное обновление кода, ассетов и метаданных |

Таблица задаёт предмет приёмки и не является разрешением на запуск проверок.

Снимок фиксируется при старте, произвольные пути в tools не принимаются, Blade и команды не исполняются. SDK — необязательная dev-зависимость.

[Команды и границы](../tools/mcp/README.md). Установка SDK выполнена; запуск, handshake, вызовы tools и приёмка в Codex не выполнялись. По отдельному согласию пользователя выполнен codex mcp add для aestetic-ui; это регистрация, не подтверждённое соединение. Опубликованный alpha.1 не перезаписывался; новый релиз с MCP не выпускался. Это частичный результат этапов 2/6, а не завершение всего MCP-плана и страниц списка/карточки/формы.
