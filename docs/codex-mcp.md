# Подключение к Codex через MCP

## Статус

Это спецификация будущей интеграции. MCP-сервер не реализован и не запущен, настройки Codex не изменены, подключение не выполнено. Имена инструментов ниже — проектируемый API, а не доступные сейчас tools.

## Цель

Во время работы над Laravel-проектом Codex получает сведения об установленной версии Aestetic UI: доступные компоненты, реальные props/slots, правила выбора, иерархию и примеры страниц.

Codex выступает MCP-клиентом, а библиотека предоставляет источник знаний. Это не задача запускать Codex как MCP-сервер.

## Что передавать агенту

| Область | Содержание |
| --- | --- |
| Компонент | Назначение, слой, API, defaults, slots, состояния, ограничения, альтернативы |
| Правила | Заголовки, отступы, действия, группировка, навигация, responsive, доступность |
| Композиция | Сценарий задачи, дерево компонентов, места под данные/действия, необходимые состояния |
| Пример | Исходный Blade и при наличии ссылка на живое представление именно этой версии |
| Доступность | planned/implemented/experimental/deprecated и поддерживаемые версии |

Обычного списка CSS-переменных и имён компонентов для выбора недостаточно. Нужны when-to-use, when-not-to-use и примеры законченных задач.

## Проектируемые инструменты

| Tool | Вход | Выход |
| --- | --- | --- |
| `get_library_info` | Запрошенная версия или список доступных версий | Версии, схема, совместимость и статус поставки |
| `search_catalog` | Версия, задача/запрос, вид, ограничение количества | Подходящие ID, назначение и статус |
| `get_component` | Версия, ID | Подтверждённый API, состояния, ограничения, примеры |
| `get_pattern` | Версия, ID/сценарий | Дерево композиции, компоненты и правила |
| `get_design_rules` | Версия, область: typography/spacing/navigation/actions и т.д. | Нормативные для версии правила и исключения |
| `get_example` | Версия, ID компонента/сценария, состояние | Blade-пример, привязка к реализации, необязательный preview URL |

Начальная интеграция — read-only. Она не пишет файлы проекта, не читает произвольные пути по внешнему параметру, не выполняет команды и проверки. Изменения кода делает Codex в обычном рабочем процессе с полномочиями текущего проекта.

## Версии и отсутствие реализации

- Codex читает composer.lock/манифест проекта обычными разрешёнными инструментами и определяет установленную версию. MCP не сканирует чужой проект самостоятельно.
- Все запросы компонентов/правил выполняются с выбранной версией; сервер не переключается на latest незаметно.
- Если версия недоступна, возвращаются явная причина и доступные версии. Подборка похожей версии не выдаётся за точный контракт.
- Компонент `planned` не имеет подтверждённого API. В ответе нельзя фабриковать props, пример установки и рабочий Blade.
- Поиск для генерации интерфейса по умолчанию показывает реализованные компоненты. Planned можно запросить отдельно для планирования.
- Схема API инструментов и версия каталога независимы от версии Composer-пакета.

## Рабочий процесс Codex

1. Определить framework и установленную версию библиотеки.
2. Найти сценарий страницы: список, карточка, форма и т.д.
3. Получить правила навигации/иерархии и документацию используемых компонентов.
4. Собрать страницу с библиотечными композициями и реальными props, сохраняя предметную логику у приложения.
5. При отсутствии подходящего компонента явно описать пробел; не имитировать готовый API и не добавлять случайное локальное оформление.
6. Отдельно сообщить реализацию, ограничения и фактическую приёмку. Проверки запускать только при разрешении пользователя текущего проекта.

Нужен небольшой устанавливаемый навык с этим процессом и ссылками на инструменты. Его создание и установка — последующий этап; глобальные инструкции и настройки в рамках основания проекта не меняются.

## Размещение сервера

Первый вариант — локальный MCP-процесс со STDIO, который читает установленный снимок каталога. Это позволяет использовать знания в разных проектах без обязательного запуска Laravel-workbench.

Удалённый Streamable HTTP endpoint возможен как следующий вариант для общей команды/нескольких компьютеров. Хостинг, аутентификация, URL и доступы выбираются перед публикацией. Сейчас endpoint, порт и токены не выдумываются и не настраиваются.

Снимок JSON/документов поставляется с библиотекой как fallback: отсутствие MCP не должно вынуждать агента угадывать API. Это не обещает автоматического чтения без установленного навыка/инструкций и доступных инструментов.

## Каталог и Storybook

Подготовлен [Laravel-workbench](../workbench/README.md) с 11 живыми Blade-сценариями четырёх experimental-контрактов. Он читает `previews` и API из общего реестра, рендерит файлы `catalog/examples/` и показывает исходники тех же файлов. Локальная установка выполнена; HTTP-rendering и визуальная приёмка не выполнялись. Это реализация каталожной части, а не MCP-сервера: инструменты MCP и подключение Codex пока не реализованы.

Для Blade предлагается Laravel-native живой каталог, использующий реальные components и scenarios. Он должен давать возможности, нужные от Storybook: состояния, controls, code snippets, темы, viewport и примеры страниц.

У Storybook уже есть MCP, но AI-возможности находятся в preview, а docs-toolset зависит от framework и не предоставляет manifest API для Blade из коробки. Поэтому MVP не рассчитывает на автоматическое извлечение Blade API готовым Storybook addon. Storybook остаётся возможным адаптером, если отдельный технический прототип докажет полезность без дублирования шаблонов.

## Критерий готовности интеграции

На синтетическом проекте Codex получает документацию правильной версии, находит композицию и создаёт список/карточку/форму с существующим API. Недоступная версия и planned-компонент дают явный ответ. Факт настройки MCP и результаты разрешённых проверок фиксируются отдельно от наличия файлов сервера.
